# Plan: `cinch workflows` / `cinch workflow NAME` — a stable invocation surface

Status: in-progress

## Context

`dca1e13d6d38` (and its follow-up renames) already solved the main problem:
instead of hand-authoring a thin `SKILL.md`-style pointer file per workflow
per agent harness, `cinch render` now generates one `index.md` (a trigger
table) alongside the rendered workflows, and a consumer repo adds a single
line to `AGENTS.md`:

```
Workflows: see .docs/workflows/index.md for what's available and when to use it.
```

That line is the last piece still hand-authored, and it hardcodes a path —
`.docs/workflows/index.md` — that depends on `paths.docs` from
`.docs/manifest` (`internal/cinch/check.go`'s `docsPathValue`/
`ResolveDocsRoot`). If a consumer overrides `paths.docs`, that AGENTS.md line
silently goes stale: a fact duplicated outside cinch's control, which is
exactly the "one fact, one place" / derivability failure mode this project's
own principles (`.docs/PRINCIPLES.md`, `internal/cinch/docs/philosophy.md`)
exist to prevent. It's also not really an *invocation* — it's a path an
agent must independently choose to go read.

The fix: give agents a stable **command** instead of a path. Any agent
harness with shell access (i.e. virtually all of them) can run it directly,
with zero per-harness files — hand-authored or generated. This directly
answers "invoke cinch workflows without creating agent skills," and it also
closes the staleness gap: `AGENTS.md` in a consumer repo becomes

```
Workflows: run `cinch workflows` to see what's available and when to use it, and `cinch workflow <name>` to load one.
```

— a command, not a path, so it's immune to `paths.docs` reconfiguration.
The existing slash-command-UX trade-off (a harness with native `/domain`
typing still has no native binding) is separate and stays as documented;
this change fixes path staleness/invocation ergonomics, not that.

Both new commands are thin readers over what `cinch render` already wrote —
no new rendering logic, no new template/index format, single source of
truth remains the rendered files on disk. They never render implicitly
(same separation `check`/`ignores` already keep from `render`).

## Design decisions

- **Two flat top-level verbs (`workflows`, `workflow NAME`), not a nested
  subcommand.** main.go's dispatch is a flat `switch os.Args[1]` — no
  subcommand parsing exists anywhere in this codebase. `ignores` is already
  precedent for a plural, no-argument listing verb; `workflows` mirrors it.
  `workflow NAME` mirrors `check [MSGFILE]`'s positional-arg shape.
- **Print verbatim, including the generated header — no stripping.**
  Stripping `header()`'s `<!-- generated by cinch ... -->` line would need
  `workflow.go` to know that format's exact structure, which is a second
  place required to stay in sync with `render.go` — the very problem this
  feature removes, just relocated. The header is one harmless line and
  doubles as provenance.
- **Share the `"workflows"` subdirectory name as a constant** between
  `render.go` and the new file, rather than leaving it as the inline string
  literal `docsRoot + "/workflows"` `render.go` currently has.

## Implementation

### New file: `internal/cinch/workflow.go`

```go
const workflowsSubdir = "workflows"

// listWorkflowNames returns the sorted base names (no ".md") of every file
// under docsRoot's workflows/ subdirectory. Returns the raw os.ReadDir
// error (checkable with os.IsNotExist) when render hasn't run yet.
func listWorkflowNames(docsRoot string) ([]string, error)

// CmdWorkflows implements `cinch workflows`: prints the rendered workflow
// index verbatim to stdout. Reads what render already wrote — like check
// and ignores, never renders implicitly.
func CmdWorkflows(docsRoot string) int

// CmdWorkflow implements `cinch workflow NAME`: prints one rendered
// workflow file verbatim to stdout. NAME with or without a trailing ".md".
func CmdWorkflow(docsRoot, name string) int
```

`CmdWorkflow`: trim a trailing `.md` off `name`, call `listWorkflowNames`
once (doubles as existence check and as the "available names" list on a
miss), find the exact match, `os.ReadFile` + write to stdout on hit.

Edit `internal/cinch/render.go`: replace the inline
`workflowsDir := docsRoot + "/workflows"` with the shared
`workflowsSubdir` constant.

### `main.go`

Add `workflows` and `workflow` cases after `render`, each resolving
`impl.ResolveDocsRoot(".")` first (same pattern as the `ignores` case):

- `cinch workflows` — 0 args only (else `usageError`, exit 2) →
  `impl.CmdWorkflows(docs)`.
- `cinch workflow NAME` — exactly 1 arg (else `usageError`, exit 2) →
  `impl.CmdWorkflow(docs, args[0])`.

Extend the `usage` const with both commands, in the same style as the
existing entries.

### Exit codes

| Situation | Command | Exit |
|---|---|---|
| `ResolveDocsRoot` fails (malformed manifest) | both | 1 |
| workflows dir missing (render never ran) | both | 1, actionable message naming `cinch render` |
| NAME doesn't match any rendered file | `workflow` | 2, stderr lists available names |
| wrong arg count | both | 2 |
| success | both | 0, file bytes verbatim on stdout |

This matches the existing split: precondition/state failures (nothing
rendered yet, like `render`'s missing-manifest case) are exit 1;
argument-shape problems the caller controls (like `check`'s "too many
arguments") are exit 2.

## Tests

### `internal/cinch/workflow_test.go`
(Only `listWorkflowNames` returns a value worth unit-testing — `CmdWorkflows`/
`CmdWorkflow` print straight to stdout, same as `CmdCheck`/`CmdIgnores`/
`CmdRender` today, which have no unit tests for that reason; they're covered
CLI-level.)

- `TestListWorkflowNames_ReturnsSortedBaseNames` — write
  `workflows/{b.md,a.md,index.md}` under a `t.TempDir()` via the shared
  `writeFile` helper (`internal/cinch/links_test.go`), assert
  `["a","b","index"]`.
- `TestListWorkflowNames_MissingDirReturnsNotExistError` — empty temp dir,
  assert `os.IsNotExist(err)`.

### `tests/cli_test.go`
(mirrors `TestRender_EndToEndAndIdempotent`, `TestIgnores_ListsDeclarationsWithReasons`,
`TestRender_MissingManifestFires`, `TestCheck_CustomDocsRootFromManifest`)

- `TestWorkflows_PrintsIndexVerbatim` — render, then `workflows`; stdout
  byte-equal to the on-disk `index.md`.
- `TestWorkflows_NotRenderedFires` — no prior render; exit 1, stderr
  mentions `cinch render`.
- `TestWorkflows_TooManyArgsFails` — `workflows extra`; exit 2.
- `TestWorkflow_PrintsNamedFileVerbatim` — after render, `workflow
  maintain-domain` and `workflow maintain-domain.md` both exit 0 and both
  byte-equal the file on disk.
- `TestWorkflow_UnknownNameListsAvailable` — `workflow bogus`; exit 2,
  stderr contains known names.
- `TestWorkflow_NotRenderedFires` — no prior render; exit 1.
- `TestWorkflow_RequiresExactlyOneArg` — 0 args and 2 args; both exit 2.
- `TestWorkflow_CustomDocsRootFromManifest` — the load-bearing test: write
  `.docs/manifest` with `paths.docs = mydocs`, render, then run `workflow
  maintain-domain` with no path argument anywhere and assert it resolves
  correctly — proving the command (not a hardcoded path) is what stays
  correct under reconfiguration.
